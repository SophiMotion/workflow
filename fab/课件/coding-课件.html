状态机与AI协作编程

把自然语言需求转成可检查的行为规则。

能解释状态转移，审查AI生成的逻辑，并用正常与异常用例验证。
01 / 提出问题

今天要解决什么？

能解释状态转移，审查AI生成的逻辑，并用正常与异常用例验证。

使用的材料

浏览器或编程环境、版本记录工具；先模拟后连接设备。

留下的成果

状态图、提示词与审查记录、测试用例、程序版本。

02 / 理解模型

先把关系说清楚。

先写输入、状态和输出，再让AI生成实现草稿。每段生成代码需要解释、最小测试和版本记录。学生决定需求与判断证据，教师按需要解释概念与示范安全操作。

待命 → 接单 → 运行 → 到达 → 待命；任一活动状态遇到故障 → 停机。
03 / 算例与边界

一起检查这个例子。

若电量低于课堂设定阈值，待命状态拒绝接单并提示；运行中发生通信超时则先停机。写出这两条测试后，再检查程序是否实现。

追问：哪些是假设？换一个条件，结论是否会改变？

04 / 动手实践

做一次可以复查的实验。

  1. 画状态图，为每条转移定义触发条件和动作。
  2. 给AI明确接口、单位、限制和需要通过的测试。
  3. 逐段阅读与解释生成代码，先用模拟输入验证。
  4. 执行至少一个正常路径和两个异常路径，保留修改原因。

05 / 判断与讨论

AI生成的代码能运行，是否说明功能正确？

先独立判断，再与同伴比较证据。

展开教师参考

不一定。需要核对需求与边界条件，尤其是超时、重复消息、输入缺失及状态冲突。

06 / 检查与改进

怎样知道自己做对了？

学生能独立解释一条正常与异常路径，测试记录对应当前版本。

常见问题：用演示成功替代异常测试；无法解释的生成代码直接连实物。

交付：状态图、提示词与审查记录、测试用例、程序版本。

07 / 反思与迁移

把今天的证据带到下一个环节。

追问：你认为AI在哪一步最可能误解需求？如何写一个会暴露这个错误的用例？

写下一个你改变过的判断，并指出触发变化的数据或观察。
